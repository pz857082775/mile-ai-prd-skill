# 润色优化 与 基于现有功能补全 的工作流

本文件是 `SKILL.md` 第十、十一节的细化，供 `/polish` 与 `/enhance` 阶段遵循。

## A. /polish 润色优化已有 PRD

**目标**：把用户给的已有文档变成"逻辑零错误、无缺口、高质量、可被执行"的 PRD，不推倒重来。

### 步骤
1. **通读建图**：用一句话概括文档主旨与范围；列出所有实体、状态、接口、页面。
2. **逻辑体检（零错误）**：
   - 矛盾：同一概念两种定义、同一流程两种说法。
   - 断链：功能提到数据但无表、接口提到字段但无定义、引用了不存在的 ID/章节。
   - 状态机不闭环：状态有入口无出口、无终态、非法迁移未禁止。
   - 数据流不闭环：写入无读取/展示/回滚。
   - 权限不闭环：敏感操作无鉴权/越权防护。
3. **缺口补全**：缺库表/缺 API/缺边界/缺非功能/缺合规 → 补（用 `[补全]` 标注）。
4. **提质**：
   - 去啰嗦：删铺垫、抒情、重复，只留清晰逻辑。
   - 统一跨切面：命名/路径/响应信封/分页/软删/ID/校验。
   - 加四维标签：每个功能补 实用/美观/逻辑/盈利 评估。
   - 加前瞻：补可演进/插件化/未来场景。
5. **分级报告**：每条问题标 `CRITICAL/HIGH/MEDIUM/LOW` + 修改建议；用户确认后输出优化版（可 diff 呈现）。

### 输出格式
```
# PRD 润色报告
## 逻辑错误（必改）
- [CRITICAL] 位置：问题描述 → 建议
## 缺口补全
- [HIGH] 缺失 X → 建议补 Y
## 提质项
- [MEDIUM/LOW] …
## 优化后文档（/export）
```

## B. /enhance 基于现有界面/功能补全需求

**目标**：用户已有界面/功能/草图，帮他把功能补全得更完善、更强、更赚钱。不推翻原设计，只增强。

### 步骤
1. **解析现状**：识别已有页面/组件/功能与核心场景；列出已覆盖点。
2. **发散补全（提"几点更完善的需求"）**，从以下维度各想 2-3 条：
   - **健壮性**：异常态、空态、加载态、超时/重试、弱网、断线重连。
   - **权限与安全**：角色细分、越权防护、审计、隐私合规。
   - **数据洞察**：看板、统计、导出、筛选、搜索。
   - **增长与裂变**：分享、邀请、海报、勋章/成就、签到。
   - **个性化与智能**：推荐、个性化配置、AI 辅助（如智能填写/摘要）。
   - **商业化**：会员、付费功能、广告位、打赏、内购、增值服务。
   - **体验增强**：手势、动效、快捷键、无障碍(a11y)、深色模式。
   - **前瞻**：多语言、多端、开放 API、插件、未来场景预留。
3. **四维价值**：每条补全给"为什么"——实用性（解决什么）、美观性（体验提升）、逻辑性（如何自洽）、盈利性（变现/留存/增长贡献）。
4. **并入文档**：补进功能地图（标 P0/P1/P2）与功能规格（Given/When/Then + 边界），原功能保留。

### 输出格式
```
# 功能补全建议（基于现有 X）
## 1. [补全功能名]（P?）
- 为什么：实用[…] / 美观[…] / 逻辑[…] / 盈利[…]
- 逻辑：作为[角色]，希望[…]，以便[…]
- 验收：Given[…] When[…] Then[…]
- 边界：[…]
## 2. …
```

## 通用约束
- 不啰嗦：每条只写清逻辑。
- 逻辑零错误：补全项必须与原文无矛盾，引用原文已有实体而非新建悬空。
- 标记清晰：`[补全]` / `[假设]` 区分新增与未确认。
